# 2026-10-21 — TSK-001 AC3: tracking-cycle start through the patched mqttv4

**Change under test:** `patches/mqttv4-0.4.1-motion-start-e6.json` (mqttv4 sha256 `80e5d1d7…1ce972`), deployed 00:27:15Z.
**Mode:** events, short functional window (not the 48 h / 7 d acceptance run).
**Window:** 00:30:43Z (tracking on) to 00:36:47Z (tracking off), about 6 min, one person walking past.

## Settings

- `camera.conf`: `SENSITIVITY=medium`, `MOTION_DETECTION=yes`, `MOTION_TRACKING=no` at start. Tracking was switched with `ipc_cmd -o ON` / `-o OFF`. mqttv4 rewrites `camera.conf` on each `IPC_MOTION_TRACKING_ON/OFF` (mtime 00:36:47Z = the OFF), so the file went `yes` then back to `no`
- Camera uptime at start: about 650 s (booted 00:19:43Z, after the RTSP password change)
- Patches deployed: only the mqttv4 record above
- RTSP client: HA stream may have been open (not checked); no CPU claim is made

## Method

Raw IPC log: `2026-10-21-tsk001-ac3-ipc.log` (this folder).

- IPC: `ipc_read -n 3 -d` on `/ipc_dispatch_3`. Each hex line was prefixed with `/proc/uptime` read by the shell builtin `read`, so the loop spawned no tools. The log ran on `/tmp/sd/yi-dome-hack-logs/tsk001-ac3.log` (78 lines, 5.5 kB). Uptime was converted to UTC from one anchor (`date -u +%s`, 1 s resolution).
- MQTT: an agent on the broker host ran an HA websocket `mqtt/subscribe` on `<prefix>/#`. Times are when HA received each message, to the millisecond.
- Clock offset: the camera ran 0–1 s ahead of the Mac, measured with a single SSH round trip. No NTP-grade offset to the broker host was taken, so the deltas below carry about ±1 s and are not ADR-0005 latency numbers.

## Before (stock 0.4.1)

No stored baseline in this folder. The stock evidence is in `docs/evaluation.md` (Need): with tracking on, the `0xe6`-only starts at 00:36:03 and 00:38:42 (2026-10-21, camera time) produced no MQTT `motion_start`, so 2 of 2 tracking-cycle starts were lost.

## After (patched)

| IPC (camera clock) | id | MQTT (HA received) | payload | delta |
|---|---|---|---|---|
| 00:31:31.99Z | `0x7c` | 00:31:32.739Z | motion_start | +0.75 s |
| 00:31:33.01Z | `0xe6` (inside open event) | 00:31:34.039Z | motion_start (duplicate) | +1.03 s |
| 00:34:23.97Z | `0x7d` | 00:34:24.754Z | motion_stop | +0.78 s |
| **00:34:26.03Z** | **`0xe6` only** | **00:34:26.288Z** | **motion_start** | **+0.26 s** |
| 00:36:25.51Z | `0x7d` | 00:36:26.288Z | motion_stop | +0.78 s |

- **AC3 passes.** A tracking-cycle start sent only as `0xe6` produced an MQTT `motion_start` within 5 s, even allowing for clock error.
- The full `0xe6` message is `01 00 00 00 02 00 00 00 e6 00 e6 00 00 00 00 00` (16 bytes, zero tail). It equals the patched `IPC_MOTION_START_C` exactly.
- **End of a tracking-cycle event:** both events end with a plain `0x7d` (`IPC_MOTION_STOP`). No other message closes a cycle.
- No start was lost: 2 starts at the event level, 2 `motion_start` in MQTT, plus 1 duplicate. Before: 2 of 2 lost; after: 0 of 2 lost (n is tiny, and the 48 h run is TSK-008).

## Side effects seen

- Duplicate `motion_start`: an `0xe6` inside an event already opened by `0x7c` now publishes a second `motion_start` with no stop between. The HA binary sensor stays `on`, so it is harmless there. Automations that trigger on the start message itself fire twice.
- The duplicate start also triggers a second snapshot in mqttv4's IPC thread. That grab returned an empty `motion_detection_image` (00:31:35.230Z, 0 bytes), which overwrote the good image from 1.2 s earlier. This is the likely cause of `camera.camera_dome_motion` returning 500. De-duplicating starts inside an open event is new logic, so it is a source change under ADR-0007.
- `motion_files` for event 1 arrived at 00:35:34Z, 70 s after its stop. Event 2's `motion_files` was outside the window, which closed 24 s after its stop. Not checked.
- Other `rmm` traffic during tracking: PTZ `0x4006`/`0x4007` bursts and unknown `src=0x10` ids `0xe7` (about every 17 s) and `0xe8`. These are not motion events.
