# Evaluation: yi-dome-hack

**Feasibility:** feasible with caveats — both fixes can be applied as in-place data/instruction patches to the shipped binaries (no compiler); the hisiv300 toolchain is only needed for later source changes and has no public image.
**Build:** build with changes — stripping yi-hack services is refuted as a CPU lever; the project targets event reliability, plus the rmm mic pipeline (~29% CPU) as the one real CPU lever; the replacement assumption held at the IPC level in a live test; TSK-001 tests it end to end through the patched bridge.
**Goal:** learning — by 2026-11-30, with auto-tracking on: 0 lost motion starts over 7 days, motion to MQTT broker < 1 s, still image (`res=low`) median < 2 s and max < 4 s, boot to MQTT connect < 30 s, 1-min load average (mean of 3 × 300 s windows) ≥ 20% below stock 0.4.1 on the same settings.

## Need
Pain: Home Assistant misses motion starts from the Yi Dome 720p while the camera keeps recording SD clips; the camera runs at load 5–10 with ~1 MB free RAM, stills take 4–13 s and boot to MQTT takes 46 s. Evidence: live measurements on 2026-10-20/21 (broker-host session report and Mac probe: load 7–8, 0% idle, 728 kB free) and an IPC sniffer trace proving the root cause below.
Root cause (static analysis of `rmm`, `docs/research/rmm.md`): inside a tracking cycle `rmm` sends the motion start as IPC id `0x00e6` (`send_motion_flowwith_start_msg`) instead of `0x007c`; `mqttv4` 0.4.1 matches only `0x7c` / `0x7009`, so HA gets stops but no starts. The `0x4007` bytes the live sniffer saw are `rmm_ptz_direction_ctrl_stop` (PTZ stop), not a start. Confirmed live on 2026-10-21 (validation below). The `_2` sniffer also logged `0xe6` each time, in the burst `0x4006` → `0xe6` → `0x4007` (00:38:42, 00:40:07, 00:41:36); the `0xe6`-only starts at 00:36:03 and 00:38:42 produced no MQTT `motion_start`, which is the proof of the loss.
Workaround today: auto-tracking off (`MOTION_TRACKING=no`), power cycle when MQTT motion stops. Cost: loses the dome's main feature (tracking) and needs manual intervention; the same tracking engine also turned the PTZ to the wall.
Why now: the 2026-10-20 motion-loss investigation found the cause and a firmware-level fix; upstream is idle since 2024-04, so no fix will come from there.

## Feasibility
- Hardware: Hi3518EV200, ARM926EJ-S (ARMv5, ~300 MHz), 18.6 MB Linux RAM, 16 MB NOR, SD card, OV9732 sensor. `rmm` (closed stock binary) holds ~51% CPU: mic pipeline (speex preprocess + AAC encode) ~29%, software motion detection ~10%, ISP ~7.6%; video encoding is hardware. The yi-hack side totals ~5% (plus `rRTSPServer` 3.9–4.9% on the low stream). The mic pipeline can possibly be stopped at runtime with `ipc_cmd -I OFF`, else by a one-instruction `rmm` patch (both untested; may affect SD clip audio, `mp4record` and two-way talk); see the second assumption below.
- Binary patching: `rmm` (1.6 MB, stripped, ~2 170 exported symbols, file offset = vaddr − 0x8000) and `mqttv4` can be patched in place. Chosen motion fix (ADR-0003): `mqttv4` file offset `0x5928` (`IPC_MOTION_START_C`, unique; `rmm` never sends `0x7009`) rewritten to match `0xe6`, MQTT path only. Rejected: `rmm` file offset `0x2dac4` `e6`→`7c`, which every consumer (`mp4record`, `cloud`) would see. `rmm` patches stay only for the mic pipeline. Holds statically; untested on the camera.
- Toolchain: yi-hack-v5 builds with `arm-hisiv300-linux-uclibcgnueabi` at `/opt/arm-hisiv300-linux` (`src/mqtt/compile.mqtt`); the repo does not ship it and no public Docker image was found. Needed for the still-image target (snapshot off the IPC thread in `mqttv4`, faster grabber) and for moving the RTSP password out of argv; fallback is a static ARMv5 build (e.g. a musl/uClibc ARMv5 toolchain in a container). Holds: a static dropbear 2026.94 from the Bootlin `armv5-eabi--musl--stable-2026.08-1` toolchain ran on the camera on 2026-10-22, (`docs/measurements/2026-10-22-tsk005-static-dropbear.md`; RAM cost vs the dynamic stock build still to be compared by Pss in TSK-010).
- Still image: the < 2 s target is reachable and already met on 2026-10-22 (TSK-004 step 2 state). CGI `snapshot.sh?res=low`: median 1.05 s, max 1.63 s, of which the `imggrabber` grab is 0.57 s. MQTT motion image: 1.11 s after `motion_start` (0.5 s `MOTION_IMAGE_DELAY` + grab). The 4–13 s did not reproduce. What remains is the grab blocking `mqttv4`'s IPC thread for about 1.1 s per start. In the run, only RPT-001 duplicate starts queued behind it; event-opening starts were not delayed (TSK-006). Evidence: `docs/measurements/2026-10-22-tsk005-snapshot-split.md`.
- Build host: Mac is arm64; OrbStack runs the linux/amd64 Bootlin toolchain image under Rosetta (`build/build.sh`); a dropbear build takes about a minute. Holds.
- Install: yi-hack-v5 already runs from the SD card (`/tmp/sd/yi-hack-v5`), so a fork can replace files there without further NOR writes. The flash already carries the yi-hack boot hook (`/etc/init.d/S20yi-hack-v5`, `/home/yi-hack-v5`): with no `/tmp/sd/yi-hack-v5` it starts the stock Yi apps. Holds.
- Integration: HA's `yi-hack_ha_integration` 0.6.0 needs MQTT default topics plus the httpd CGIs (`links.sh`, `snapshot.sh`, config); kept in scope. Holds.

## Gap
No alternative fixes the tracking-cycle motion start on this camera while keeping the stock video pipeline and PTZ; a one-value patch to `mqttv4` plus a single-target, cloud-off build does.

## Viability
Learning: the build exercises ARM binary reverse engineering and in-place patching of closed binaries, IPC reverse engineering (POSIX message queues between `rmm`, `dispatch` and `mqttv4`), embedded Linux init and resource tuning on 18 MB RAM, cross-compiling for ARMv5/uClibc, and MQTT/HA integration. Scope forces it: the motion task cannot pass without reading live IPC traffic and patching a shipped binary, and moving the RTSP password out of argv cannot be done without a cross build (the still-image target turned out to be met without one; TSK-005).

## Riskiest assumption
With auto-tracking on, `rmm` emits `0x00e6` as the only start message for tracking-cycle motion starts (2 observed) and `ipc_multiplex.so` copies it to `mqttv4`'s queue `/ipc_dispatch_1`, so a one-value patch makes HA see every start — validation: 5 min with tracking on (runtime `ipc_cmd -o on`, config untouched), `ipc_read -n 3 -d` while walking past — result: held end to end on 2026-10-21 through the patched bridge (TSK-001: an `0xe6`-only start at 00:34:26.03Z UTC gave MQTT `motion_start` 0.26 s later, and both tracking-cycle events ended with a plain `0x7d`; `docs/measurements/2026-10-21-tsk001-mqttv4-e6.md`). Earlier IPC-level run (2026-10-21 01:41:57–01:46:57 camera time, one walk-in: `0x7c` at 01:41:59, `0x6003` at 01:42:00, `01 00 00 00 02 00 00 00 e6 00 e6 00` at 01:42:01, then PTZ `0x4006`/`0x4007` pairs, no `0x7d` inside the window; queues `_2` and `_3` both received every message). This run's `0xe6` fell inside the event already opened by `0x7c`, so the loss itself is proven by the earlier `0xe6`-only starts (see Need).
Second assumption (CPU target): stopping the mic pipeline cuts `rmm` CPU by about 25 points without breaking SD video recording — validation: `ipc_cmd -I OFF` for a 5-min sampling window, then check a new SD clip plays — result: partly held on 2026-10-21 (TSK-003). `ipc_cmd -I OFF` had no effect (rmm 52.8 % to 52.2 %). Skipping speex cut 7.3 points with recording intact. Not starting the audio thread cut 30.4 points (52.8 % to 22.4 %), but `mp4record` waits forever for an AAC frame and records nothing (`docs/research/mp4record.md`). the owner uses only live view, so SD recording leaves the scope (ADR-0008) and the load target stays.
Replaces: "a patched `mqttv4` built with the hisiv300 toolchain…" — superseded by static analysis: no compiler is needed for the fix, the message id is the open risk.
Replaces: "stripping yi-hack services frees real CPU and RAM" — refuted by per-process `/proc/<pid>/stat` deltas: `rmm` 44–53%, removable services ~5% combined.

## Kill criteria
Stop if by 2026-11-15 the patched camera still loses tracking-cycle motion starts over 48 h with tracking on; then stay on stock yi-hack-v5 0.4.1 with tracking off. If by 2026-11-10 TSK-003 cuts `rmm` CPU by fewer than 10 points, drop the load target and re-scope.
